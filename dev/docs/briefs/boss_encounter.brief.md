## 使用者的構想（原話轉述）

> Boss 戰主要是機制。Boss 我在考慮直接用 3D model 弄成類似會發砲的祭壇，然後周圍挖一圈不可跨越的壕溝，逼玩家殺怪後開始想辦法拿拾取物破壞。

拆成四個機制主張：

1. Boss 是**靜態建築**，不是會走路的身體。
2. Boss 的攻擊是**砲擊**（有前搖、有預告、越牆）。
3. 壕溝讓玩家**近戰打不到**，所以近戰不是解法。
4. 解法是**投擲**，而彈藥來自**殺小怪掉的拾取物**，所以戰鬥迴圈是「清場 → 撿 → 丟」。

這個設計最漂亮的地方是它把 demo 已經有的三條線綁在一起：砲擊預告、投擲、破石。它不需要新的動詞。

## Boss 的畫面怎麼進遊戲：不需要 three.js

**這是這份 brief 最重要的一段，接手的 Agent 如果只讀一段就讀這段。**

先講一件容易誤判的事：遊戲本體 `src/presentation/canvas-gameplay-renderer.ts` 是 **Canvas 2D**，沒有 Three.js，three.js 只活在 `src/sandbox/` 的兩個實驗裡（經 debug hub 進入）。所以「載入一個 GLB 放進遊戲」現在做不到。

**但遊戲已經有一個立體方塊渲染通道**，在 `src/presentation/render-scene.ts` 約 170 行的 `RenderBox`：

```
RenderBox = { id, x, y, halfX, halfY, bottom, top, color, topColor? }
```

它的註解寫得很清楚：一個 box 以自己的各個面繪製、遵守深度緩衝，所以遮擋正確、每面各自著色、繞著走時輪廓會變。現在用它畫的東西有：詛咒祭壇（含被打壞的碎塊）、祝福台的四根角柱、溫泉、撤離罐、樓梯口、迫擊砲台。繪製時跟 sprite 依深度交錯、由遠而近畫（`canvas-gameplay-renderer.ts` 約 2039 行）。

**所以麥塊風格的 voxel 祭壇跟這個渲染器天生同構。** voxel 建模腳本輸出的 `{center, size, material}` 跟 `RenderBox` 是同一個東西，只差一次座標轉換與一張材質對照表。

### 走這條路的三件事

**一、效能的風險在 Canvas 2D，不在 WebGL。** 13,068 triangles、15 個材質群組在 WebGL 是零成本。但現在整層樓所有立體物加起來大概只有幾十個 box（程式裡的 box 字面量約 43 個，加迴圈展開約 60–120）。**1089 個 box 是整層預算的十倍以上，而且只是一個物件**，還會把深度排序清單從一兩百項推到一千三百項，那個排序每幀都做。

**二、必須先減量，而 voxel 風格特別好減。** 大量方塊看不到（底座內部、被上層蓋住的、堆疊實心區）；同材質共面合併（greedy meshing）能把 21×21 的底座從 400 多個方塊塌成 1 個。**現實目標 80–150 個 box**，跟現有一間側房的 fixture 同量級，外輪廓與金邊細節都保得住。

**三、`RenderBox` 是軸對齊的，沒有旋轉欄位。** 那個模型用 ±45° 交錯做出來的鎖鏈畫不出來，要改成軸對齊的階梯狀或砍掉。拱門、火盆、階梯、符文鑲嵌、懸浮核心全部軸對齊，1:1 可轉。

### 建議路徑

```
voxel 資料
  → dev/tools/ 的離線轉換工具（合併同材質共面方塊、丟掉看不見的）
  → 一張 RenderBox 的 authored 表進 src/content/
  → 場景建構讀表，擺在 boss 房
```

三個附加價值：它本身就是 data-drive 那條線的實例；**將來 three.js 化時這張表不用重做**（voxel 表跟渲染器無關，直接餵 InstancedMesh）；視覺語言跟方塊骷髏一致，而方塊骷髏已經定案是原型。

**明確不建議走烤圖那條路。** 一座 21×22×16 的建築烤成 8 向 billboard，玩家走到兩格外就會看出是紙片，而且會跟牆穿插。身體可以烤（小、在遠處），建築不行。

### 量它的工具是現成的

`npm run capture` 用 headless 瀏覽器跑 demo、固定亂數種子、寫出 `capture-output/latest/stats.json`（frame timing + world counts）與前後對照圖。它只觀察不判定。**最省事的驗證**：先塞一個假的 300-box 結構跑一次 capture 看 frame time，半小時就有答案，而那個數字直接決定祭壇的細節預算。

## 已答的問題

1. **Boss 放在哪裡？** 一間 room。主區也是 room 之後，Boss 房就是 room 種類裡的一種，不需要新結構。
2. **一場 run 有幾次 Boss？** **固定有，每張 map 都有。** Demo 之後會需要多種 Boss 房變體 —— 至少一個固定建築式、一個大型 3D entity 式 —— 但後者 Demo 之後再說。
3. **壕溝擋不擋東西？** **只擋玩家的腳。** 不擋敵人、不擋砲彈、不擋投擲物。
4. **彈藥不夠怎麼辦？** **無限，但來源是持續產生的骷髏。** 殺骷髏 → 撿拾取物 → 砸 Boss。所以戰鬥的節奏由 room 的 respawn 速度決定，而 respawn 已經定案是 room 的屬性。
5. **Boss 的 dead zone。** 看工程量選最省的：**如果復用現有砲台的兩格 dead zone 比較簡單，就把壕溝挖成兩格寬的圈**，讓地形直接等於 dead zone，規則一行都不用改。

## 還沒有答案的問題

1. **打贏 Boss 換到什麼？** 現有獎勵通貨有三種：祝福、封印獎勵（帶到撤離房才知道是什麼）、以及開路。樓梯之後會廢掉，主任務改成開撤離，所以「開路」這個選項的意思會變。這題要在 plan 寫成之前答。
2. **Boss 有沒有階段？** 生命值、階段、死亡表現全部沒有設計。
