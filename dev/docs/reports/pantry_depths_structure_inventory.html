1. structure 三族總覽

你說的三類在程式裡沒有共同的父型別，也沒有共同的詞。它們是三組彼此獨立的表，分散在三個層裡，靠 PropKind 與 EnemyAppearanceId 兩個 union 串起來。以下是各族的實際邊界。

Drop / 掉落物

PropKind 13 種。躺在地上、能撿、能丟、能射。三張表分別管行為、重量、外觀。

Entity / 實體

DemoArchetypeId 7 種 demo 行為 × EnemyAppearanceId 10 種外觀 × 4 套骨骼圖集。另有一組 9 筆的舊表尚存。

World / 立體結構

沒有 3D 模型檔。是 RenderScene 的 11 種繪製基元、8 種 tile kind、7 組 box 佈景、4 個 decor preset。

1.1 「3D model」在這個專案裡實際是什麼

專案裡沒有 mesh、沒有 glTF、沒有 voxel，渲染器是 canvas-gameplay-renderer.ts 的 raycaster。 因此「立體」是靠四種手段做出來的，四種各有自己的資料形狀：

  • 柱體幾何：RenderBox，軸對齊方盒，會被深度緩衝正確遮擋、逐面著色，繞著走輪廓會變。祭壇、樓梯、路障、迫擊砲都是一堆 box 疊出來的。
  • 軟體：RenderBlob，一疊會形變的環，用來畫史萊姆 —— 它不是圖片，所以能被壓扁、拉長、劈成兩半。
  • 看板：RenderSprite，永遠面向鏡頭的圖，三種擺法（billboard / ground / wall）。骷髏、掉落物、裝飾都走這條。
  • 牆與地板：不是物件，是逐像素從材質取樣的 RenderSurface / RenderFloorMaterial / RenderFloorDecal。

1.2 層與依賴方向

src/core/ 規則基元（grid、combat、run-state） ▲ src/content/ 授權資料：PROP_KINDS、EnemyAppearanceId、骨骼圖集、decor preset、三張 JSON 表 ▲ ▲ src/demo/ 行為表：throw-weight、enemy-archetypes、maze、world ▲ src/presentation/ 繪製語彙：RenderScene 型別 + raycaster
一個刻意的倒掛。 PROP_KINDS 這個「有哪些掉落物」的清單住在 src/content/presentation/prop-display-schema.ts， 而不是住在使用它的 src/demo/throw-weight.ts 旁邊。原因是層規則：content 只能 import content 與 core，驗證器沒辦法往上抓 demo 的 union。所以清單放下層、demo 用 type DemoPropKind = PropKind 別名接回來 —— 這是唯一能保證「新增一種掉落物就一定得補顯示列，否則編不過」的排法。

markerOffset 為負是刻意的取捨，不是打錯：正值把預警標記浮在頭上，負值把它壓進身體。 高個子頭上的標記在「這東西已經有危險」的距離會離開畫面，所以往下壓是用剪影乾淨度換可見度 —— Entity Workbench 旁邊有距離滑桿就是為了這個判斷。

5. World structures（立體）

5.1 RenderScene 繪製基元

這是 demo 與 renderer 之間唯一的詞彙表。每個基元都是為了「上一個做不到的某件事」而存在的， 所以看起來重複的其實不能互換。

RenderScene 的 11 種基元
型別是什麼為什麼不能用別的代替
RenderSurface 一格牆，帶材質與可選高度 高度只在開天空時有意義：有天花板就得頂到天花板
RenderBox 軸對齊方盒，可設頂面色，bottom 可為負（沉入地板） 貼在地上的圖是貼紙；盒子有輪廓、會被遮擋、逐面著色
RenderBlob 形變環堆疊：squash / lean / wobble / sink / droop / flash / split 看板永遠是同一張圖；軟體要能被壓扁、癱軟、劈成兩半
RenderSprite billboard / ground / wall 三種擺法，支援 frame（圖集）、spin、flash、submerged、xray 授權美術唯一的入口
RenderBeam 兩端點的桿，端點各自投影 丟向鏡頭深處的木樁，用看板畫是「一張木樁的圖在後退」
RenderParticle 帶高度的彩色圓點，可加成混合 sprite 走圖片快取，四百顆三像素的碎屑走那條會爆
RenderFloorPatch 整格換地板材質 地板是逐像素取樣的，不同的地板得用名字講，不能蓋圖
RenderFloorOverlay 整格混入材質，帶 amount 血是地板的一部分，要能被踩過、被光照、被霧吃掉
RenderFloorDecal 次格解析度形狀：disc / ring / lane / sector 整格畫不出「兩格寬的圓」或「四十度角的走道」；獨立通道才不會擦掉已有的血
RenderLight 點光源 —
RenderEmitter embers / steam 兩種，可覆寫顏色 kind 說「怎麼飄」，color 說「是什麼做的」

場景層級還有 RenderSky（把天花板整個換掉的漸層背景 + 螢幕空間星點）、 wallHeight / eyeHeight（預設 1.5，就是原本寫死的那組算式）、ambient。

6. 命名整併建議

以下是建議，不是已完成的變更，程式碼一行未動。目前描述「世界裡的東西」的詞有六個， 彼此重疊且各自的分界線不在同一個維度上。

現有六個詞的實際指涉
詞在程式裡指問題
prop 13 種可撿可丟的東西 同時被用作「掉落物」與「場景道具」兩義，propBehaviour 與 volumetric props（指 box）的註解就衝突
pickup 同上，但只在骷髏部件與顯示表的註解裡 SKELETON_PICKUP_ASSETS 與 PROP_KINDS 講同一件事，兩個詞
entity 敵人。entity-display.json、Entity Workbench 名字承諾「任何實體」，實際只涵蓋敵人的繪製數值
decor 4 個貼牆／貼地的裝飾 sprite 與 box 佈景的界線是「用 sprite 還是用盒子畫」，不是「是不是裝飾」
box 祭壇、樓梯、路障、迫擊砲的幾何 是繪製手段的名字，不是東西的名字 —— 沒有「祭壇」這個型別，只有一堆 id 叫 altar-* 的盒子
tile 8 種格子 barricade / mortar 同時是 tile（碰撞、血量）也是 box 群組（外觀），兩邊沒有共同的識別

6.1 建議的分類

若統一叫 structure，建議照「它在世界裡的存在方式」切三類，而不是照畫法切：

ItemStructure

可被拿起、被消耗、位置是暫時的。今日的 PropKind 全數。

PropKind → ItemStructureId
propBehaviour → itemStructureBehaviour
prop-display.json → item-structure-display.json

BodyStructure

會自己行動、有血量、會死。今日的 DemoArchetypeId + EnemyAppearanceId。

DemoEnemyArchetype → BodyStructure
entity-display.json → body-structure-display.json

FixtureStructure

固定在格子上、不會移動、可能有血量。祭壇／樓梯／路障／迫擊砲／溫泉／撤離點／decor。

（今日不存在此型別）
decor-presets.json → fixture-structure-presets.json

三類之外，RenderBox / RenderBlob / RenderSprite / RenderBeam 維持原名 —— 它們是畫法，任何一類 structure 都可以用任何一種畫法畫出來，把它們也叫 structure 會讓這個詞失去區分力。

6.2 這件事最大的實質收穫

FixtureStructure 目前完全不存在，這是三類裡唯一有真實成本的缺口。 路障與迫擊砲的「碰撞＋血量」住在 tile 上，「外觀」住在 demo-scene.ts 的一個 build 函式裡， 兩者沒有任何共同識別；祭壇的血量住在 world.altar，樓梯的狀態住在 maze.progress， 溫泉與撤離點根本沒有狀態。新增第八種固定物要同時改四個地方，且沒有任何一處會在漏掉時失敗。 相較之下 Item 與 Body 兩類今天已經有可用的中心表，改名只是改名。
