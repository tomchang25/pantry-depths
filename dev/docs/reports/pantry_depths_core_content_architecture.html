2. 兩層的分工

src/core/ 規則

26 個 TypeScript 檔、8285 行。定義世界是什麼形狀、每幀怎麼變。不 import src/ 裡的任何其他層， 包含 content。

src/content/ 資料

19 個 TypeScript 檔（3038 行）＋ 19 個 JSON。作者決定的數字與表，全部透過 core 的契約定型。只能 import content 與 core。

兩層的關係可以壓成一句：core 說「表長什麼樣」，content 說「表裡是什麼」，而把值遞過去的是第三者。 core 從不 import content——它要讀作者的數字，一律從被注入的 GameCatalog 拿，那個值由 src/runtime/ 在 createWorld(map, GAME_CATALOG) 那一刻交進來，並由世界自己攜帶 （world.catalog）。

這不是慣例，是機器強制的（第 8 節）。它換來的具體能力是：規則可以在沒有任何資產、沒有瀏覽器的情況下被建構與步進， 這是 src/app/debug/ 底下的工作台能直接建一個世界來玩、以及 dev/tools/ 能離線跑內容驗證的原因。

3. core 的依賴分層

把 26 個模組的 import 邊做拓樸排序，得到七個依賴帶。箭頭方向是「上面的 import 下面的」，沒有任何一條反向邊 （no-circular 規則保證，唯一的例外是第 5 節那個刻意的型別限定環）。

4. core 四個領域與根層契約

4.1 根層：不屬於任何領域的五個檔

src/core/ 根目錄下的檔案是被兩個以上領域共用的詞彙。放在根層不是懶得分類，而是分類到任一領域都會製造 一條跨領域依賴。

prop-kinds.ts 27 有哪幾種可撿的鬆散物件。每一層都講這份清單 catalog、actions、death、room-contract、prop-contract、world

4.2 floor/ — 幾何，幾乎是葉領域

負責「一層樓是什麼、長什麼樣、能不能走過去」。這個領域最值得注意的性質是：五個模組裡有四個完全不知道 World 的存在，可以在沒有 run 的情況下被建構與檢查。這正是地圖與房間工作台能直接產出一層樓來看的原因。

floor/ 模組

map-contract.ts 217 一張地圖解析後長什麼樣，以及只有「蓋好的樓層」才回答得了的那些拒絕條件 room-contract

4.3 combat/ — 牽扯最深的領域

負責玩家的兩個滑鼠鍵、敵人的腦、命中與死亡。它向下抓 floor/、向旁抓 progression/、 向上抓 world/，是四個領域裡唯一同時碰到其他三個的。

combat/ 模組
檔案 行 用途 對外依賴
melee-contract.ts 58 近戰詞彙：有哪幾刀、一刀在動畫的第幾成生效。畫出來的姿勢住在 content （無）
particles.ts 193 純表演的粒子場。模擬不讀它——每一束都是已經發生的事的回聲，整包丟掉不影響規則 （無）
enemy-contract.ts 265 一隻敵人是什麼：archetype 記錄的形狀，加上每具身體都遵守的規則數字。七列 authored 資料在 content room-contract、prop-contract

enemy-ai.ts 944 敵人行為：五種心智（idle / wander / chase / attack / retreat）的單一狀態機，沒有任何外部模組決定一具身體往哪走 actions、death、impacts、particles、maze、movement、grid、bless、world
領域內部的方向也是單向的。 death ← actions ← impacts ← enemy-ai：AI 用得到落地效果與玩家動作的計算，落地效果用得到玩家動作的傷害公式， 而所有致命結果最後都收斂到 death。反向邊一條都沒有——death.ts 不 import actions.ts，這是「唯一出口」能成立的前提。

4.4 progression/ — 純葉領域

負責一次 run 累積了什麼。這是四個領域裡結構最乾淨的一個：它只 import core/catalog 與自己的契約，從不 import floor/、combat/ 或 world/。 祝福與封印獎勵完全不知道地板長什麼樣、也不知道有人在打架；是打架的那一半反過來伸手進來領獎。

5. 契約與 catalog 的型別限定環

第 3 節的分層裡 L1 標了一個環，那是刻意的，也是整個注入機制成立的關鍵。方向是這樣的：

core/catalog.ts import type { EnemyArchetype } from core/combat/enemy-contract import type { PropBehaviour } from core/prop-contract import type { BlessDefinition, ... } from core/progression/progression-contract ↓ 用這些型別組出 GameCatalog 的欄位形狀 core/prop-contract.ts import type { GameCatalog } from core/catalog ← 反向邊 export function propBehaviour(catalog: GameCatalog, kind: PropKind): PropBehaviour core/progression/progression-contract.ts import type { GameCatalog } from core/catalog ← 反向邊 export function findBless(catalog: GameCatalog, id: BlessId): BlessDefinition | undefined

兩個方向都存在，所以這在圖上是一個環。它被允許，是因為 .dependency-cruiser.cjs 的 no-circular 規則寫著 dependencyTypesNot: ["type-only"]——型別限定的環在編譯後不存在，不會讓模組初始化順序變成有意義的東西。

這個安排換到的是三件事：

  • 契約可以自己提供存取函式。propBehaviour(world.catalog, kind) 住在契約旁邊， 而不是逼每個呼叫端自己去 catalog 上挖欄位。
  • catalog 的形狀由領域決定，不是由 catalog 自己編。 新增一種敵人屬性，只改 enemy-contract.ts，catalog 的型別自動跟上。
  • content 有唯一一個必須填滿的目標。 src/content/catalog.ts 整個檔只有 27 行，就是把四個目錄的表組成一個 GameCatalog；少一個欄位就編不過。

6. content 的兩條出路

content 的每個模組都恰好透過一個 core 契約定型——這是層規則的直接後果（它只能 import content 與 core）。 但定型之後，資料有兩條完全不同的出門路徑，看懂這一點是看懂 content 的關鍵。

6.1 第一條路：組進 GAME_CATALOG，注入給規則

全專案唯一的組裝點是 src/content/catalog.ts，27 行：

export const GAME_CATALOG: GameCatalog = { archetypes: ENEMY_ARCHETYPES, propWeights: PROP_WEIGHTS, propBehaviours: PROP_BEHAVIOURS, defaultBodyWeight: DEFAULT_BODY_WEIGHT, blessCatalog: BLESS_CATALOG, blessStackingCatalog: BLESS_STACKING_CATALOG, modifierCatalog: MODIFIER_CATALOG, coreCatalog: CORE_CATALOG, coreShare: CORE_SHARE, fragmentEffects: FRAGMENT_EFFECTS, };
進 catalog 的五個模組——只有這些是規則會拿來做判定的數字
content 模組 行 對應 core 契約 填進的 catalog 欄位
enemies/enemy-archetypes.ts 261 combat/enemy-contract archetypes
props/prop-definitions.ts 349 prop-contract propWeights、propBehaviours、defaultBodyWeight
progression/bless-definitions.ts 81 progression/progression-contract blessCatalog、blessStackingCatalog
progression/modifier-definitions.ts 81 progression/progression-contract modifierCatalog、coreCatalog
progression/sealed-reward-definitions.ts 19 progression/progression-contract coreShare、fragmentEffects

enemy-archetypes.ts 是唯一一個 import 別的 content 模組的表：它從 props/prop-definitions.ts 取 DEFAULT_BODY_WEIGHT，因為一具身體被丟出去時的重量 跟一塊石頭的重量是同一種記錄。

判斷一筆資料走哪條路的規則很簡單：規則會拿來做判定的走 catalog，只影響看與聽的直供消費者。 同一個概念可以同時有兩列——敵人的血量與攻擊節奏在 enemy-archetypes.ts（走 catalog）， 牠的 sprite 縮放與錨點在 entity-display.json（直供黑盒子），兩者靠 EnemyAppearanceId 這個 core 詞彙串起來。

地圖與房間是「找到的」不是「列出來的」。 room-library.ts 與 map-library.ts 都用 import.meta.glob(..., { eager: true }) 掃整個目錄，載入時逐檔解析並驗證，而且強制檔名等於檔案內宣告的 name／id，不等就直接拋。 代價是啟動時全部解析，換到的是丟一個 JSON 進目錄就能玩，不必去改一份清單。

7. 三條跨領域路徑

前面的表說了誰依賴誰，這一節說那些依賴實際上被用來做什麼。三條都是完整的、可以照著讀程式的路徑。

7.1 一次揮劍：跨 combat → world → progression → floor

runtime 滑鼠左鍵 → combat/actions.primaryAction(world) │ 手是空的 → 選一把不同於上一刀的 cut，raiseSfx("meleeSwing") │ 只設定 world.swing / swingTotal / swingResolved = false，此時尚未有任何傷害 ▼ core world/simulation.stepWorld 每幀檢查動畫進度 │ 到達 melee-contract.MELEE_CUT_START（動畫的第幾成）才呼叫 ▼ combat/actions.resolveSwing(world) │ meleeReach / meleeDamage 讀 progression/bless 與 sealed 的加成 │ 掃描 world.enemies，命中 → combat/death.damageEnemy │ 沒打到人但前方有牆 → actions.damageWall → floor/maze 的 tile.hp ▼ combat/death.killEnemy 唯一出口：屍體動畫、掉落判定、world.kills += 1 │ 祝福給付走 world.awardBless → progression/bless.grantBless ▼ world/tasks.stepTasks 下一幀讀 world.kills，副任務達標就再付一個祝福

這條路徑說明了為什麼 combat/ 非碰其他三個領域不可：傷害數字要問 progression、命中判定要問 floor、 結算結果要寫進 world，而傷害發生的時機由 melee 契約的一個常數決定。

7.2 一次撿起並丟出：手上那一格狀態的所有權轉移

滑鼠右鍵 → combat/actions.grabAction(world) 手上有東西 → dropHeld 否則找前方可搬的敵人 → 從 world.enemies 移除，放進 world.held = { kind:"enemy", enemy } 否則找前方的掉落物 → 從 world.props 移除，放進 world.held = { kind:"prop", ... } 滑鼠左鍵 → combat/actions.primaryAction(world) world.held 存在 → swingKind = "throw" prop-contract.propBehaviour(world.catalog, kind).use === "shoot" ? shootHeld : throwHeld → 物件離開 world.held，成為 world.projectiles 裡的一筆（敵人放在 projectile.payload） world/simulation.stepProjectiles 每幀推進 撞牆 → actions.damageWall → floor/maze 撞人 → combat/impacts（爆散、串刺、釘牆） 落地 → 敵人 payload 經 impacts.checkHazards 後放回 world.enemies

整條路徑沒有任何生命週期管理——被搬運的敵人只是一個物件在三個陣列之間換位置。這是「World 是純資料」買到的最大一筆便宜。

7.3 一次撤離：progression 的兌現時刻

world/tasks.stepTasks 主任務達標 → extraction.takeSealed(world, "clean") → world.carried.push({ source }) ← 此時只知道來源，不知道是什麼 → world.terrainVersion += 1（樓梯的封印解除，幾何要重建） world/simulation.stepExtraction → extraction.stepExtraction 玩家站在 extraction 房間的踏板上 → progress.extractionSeconds += dt 離開踏板 → 歸零（傷害不中斷，只有離開會） 滿 5 秒 → extract(world) extraction.extract world.carried.map(reward => progression/sealed.resolveReward(world.catalog, reward)) ← 是碎片還是核心、核心擲出什麼詞綴，全在這一刻才決定 → sealed.bankReward 進跨 run 的銀行 → world.endRun(world, "extracted")

這是 progression/ 身為葉領域的證明：sealed.ts 提供 resolveReward 與 bankReward 兩個純粹的操作，完全不知道有踏板、有房間、有五秒。 那些全是 world/extraction.ts 的事。

8. 邊界如何被機器強制

本文件描述的所有依賴方向都不是口頭約定。.dependency-cruiser.cjs 把它們寫成規則， npm run check:boundaries 檢查，而該指令是 npm run verify 的一環 （format:check → typecheck → lint → check:boundaries → test → build）。

與這兩層直接相關的規則（severity 全為 error）
規則 內容
core-imports-only-core src/core/ 不得 import src/ 底下任何非 core 的路徑。authored 表只能經注入抵達， 不能經 import
content-imports-only-content-and-core src/content/ 只能 import src/content/ 與 src/core/
no-circular 禁止執行期循環依賴，dependencyTypesNot: ["type-only"] —— 這是第 5 節那個契約環被允許的依據
no-orphan-modules 沒有人 import 的模組會被報出來（src/app/main.ts 與 dev/tools/ 的進入點除外）
game-layer-does-not-import-tooling src/ 不得 import dev/；反向則允許 dev/tools/ 讀 core 與 content

違反邊界的意思是程式碼放錯位置，修法是移動程式碼而不是放寬規則。這句話在 .dependency-cruiser.cjs 的檔頭與專案結構標準裡各寫了一次。

9.1 新增一種東西要動哪幾個檔

這一節是前作第 ④、⑤ 兩節始終沒填的內容。清單由第 5 節的契約環直接決定——漏掉任何一列都是編譯錯誤，不是執行期驚喜。

新增一種敵人

「行為」與「長相」是兩個獨立的 union，所以這裡分兩種情況。沿用既有外觀的新敵人只需要前三步。

  1. src/core/floor/room-contract.ts — 在 MapCastKind 加入這個 id。 catalog.archetypes 是 Record<MapCastKind, EnemyArchetype>，所以這一步立刻讓下一步變成強制的
  2. src/content/enemies/enemy-archetypes.ts — 補上 archetype 那一列（血量、速度、攻擊節奏，以及要用哪個 appearance）
  3. src/runtime/surface.ts — ENEMY_DOT_COLORS 是 Record<MapCastKind, string> 的 total map，少一列編不過（小地圖上的顏色）
  4. 只有需要新長相時：src/core/combat/enemy-contract.ts 的 EnemyAppearanceId 加一個 id，並在 src/content/enemies/entity-display.json 補上以 appearanceId 為鍵的那一列 （bodyScale、錨點與標記數值）

新增一種掉落物

  1. src/core/prop-kinds.ts — 在 PropKind 加入這個 id
  2. src/content/props/prop-definitions.ts — 補上重量與行為兩列
  3. src/content/presentation/prop-display.json — 補上顯示那一列
  4. src/runtime/surface.ts — PROP_GLYPHS 與 PROP_COLORS 兩張 total map

新增一層樓（一張地圖）

  1. src/content/rooms/<id>.room.json — 需要新房間才寫；檔名必須等於檔內的 id
  2. src/content/maps/<name>.map.json — 檔名必須等於檔內的 name
  3. 不必登記。兩個 library 都用 eager glob 掃目錄，放進去就會被找到，開發時可由 /testbed/<map name> 直接進入
