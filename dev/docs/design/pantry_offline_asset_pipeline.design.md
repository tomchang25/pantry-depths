## 這份文件是什麼

外部有一份技術報告，描述某個 Three.js 太空遊戲如何用 Blender MCP 讓 agent 自主建模、烘焙資產、並接進瀏覽器 runtime。這份文件是「那套做法裡有哪些能用在 Pantry Depths、哪些不能」的一次評估。

**它不是計畫。** 沒有任何一項被排進交付，沒有任何一項被承諾。它是一份判斷紀錄，寫下來的主要目的是避免同一輪評估被重做，以及避免其中幾條「看起來很吸引人但對這個專案是負收益」的建議被重新撿起來。

**決議：所有項目一律延到 Three.js refactor 時再一併處理。** 包含原本評估為「現在就能做、成本極低」的兩項。理由見最後一節。

## 前提：這個 repo 已經有那套管線的一半

評估的起點是一個容易被忽略的事實 —— 報告的核心結論，這個專案已經在做了。

`dev/tools/skeleton-swordsman/build.py` 就是報告描述的東西：

- Python 從空場景建骨架（15 根 bone）
- 用共用 primitive kit（`dev/tools/blender-kit/primitives.py`）長出身體
- keyframe 出 10 段 action
- EEVEE 正交相機繞 8 個方向、每段渲 8 幀
- `dev/tools/generate-skeleton-swordsman.py` 用 ImageMagick montage 成 2048 atlas
- runtime 只吃烘焙結果

所以「模型即程式碼、可從空場景全量重建、離線烘焙、runtime 不碰 Blender」這個報告的中心思想，不需要移轉，已經在了。

真正值得評估的只有兩類：**報告有而這裡沒有的**，以及**報告有但對這裡是負收益的**。

## 一、目前的投影

### 可用：一條，屬於防禦性質

報告裡船艙那條管線直接用遊戲座標系寫 Blender Python，匯出時關掉 Y-up 轉換。代價是 Blender viewport 看起來躺著，好處是 Blender 裡的數字可以原封不動抄進 runtime。

對照 `dev/tools/skeleton-swordsman/build.py` 的 `aim_camera`：那裡有十幾行註解在解釋一個左手／右手座標不一致造成的 bug，最後靠一個負號硬修，代價是成品是鏡像的、劍拿在看起來像左手的那隻手上。註解自己的結論是「It is a skeleton. Nobody can tell.」

那個判斷在當下是對的。問題不在判斷，在於這個知識被存放的位置。詳見第七節。

### 不可用：報告的 height-field → normal map 那整套

報告那套解決的是「從平面 cage 往下射線打不到垂直側壁，所以 Blender 的 tangent-space normal bake 會漏掉接縫側壁」，改成烘高度場再用 NumPy 求梯度。

`src/presentation/canvas-gameplay-renderer.ts` 目前沒有 normal map，光照是按 depth bucket × warmth 快取的整張 tint。在 column raycaster 上補 per-pixel normal 光照，成本遠高於收益。**這條的價值 100% 在 Three.js 之後。**

## 二、祭壇／拒馬等 3D 固定物

現況：`src/demo/demo-scene.ts` 的 `altarBoxes` 與 `projectDemoBarricade` 都是 `RenderBox` 組裝，renderer 逐面畫、逐 column depth test，面的明暗是三個常數（東西向側面 1、南北向側面 0.78、頂面 brighten 1.28）乘上距離衰減。

### 明確不做：把祭壇烘成 Blender sprite

報告那套之所以成立，是因為船艙是靜態的。祭壇不是 —— 它按 `wear` 逐級改變形狀並掉出 debris，拒馬的 spike 也隨損壞下降。烘成 billboard 會變成 8 方向 × 5 損壞階段 = 40 幀，而且會失去 box 現在免費拿到的逐 column 遮蔽（可以繞著走、會被牆正確切一半）。

**純虧，不要做。** 這條記下來的目的就是防止它被重新提案。

### 可用：報告的「凹槽要切進去」原則，翻譯成明暗而不是幾何

報告反覆強調不要把細節做成黏在表面的盒子，要 inset 進去，因為光線需要描述出外框、斜面、深度、內部陰影。

在 box-based 的 canvas renderer 上，這條的可行翻譯是**接觸陰影**。而這個技巧在這個 repo 裡已經有一個成熟的先例：牆的繪製有一段「Contact shadow where the wall meets the floor」，註解寫得很白 ——「沒有它，每條走廊都像立在地磚上的紙板」。

同一句話原封不動適用於祭壇和拒馬：現在每個面從上到下是均勻色，讀起來像立起來的紙板而不是放在地上的物件。

牆那段連做法都示範了：底部約 18% 高度分成兩條實心橫帶，上淡下深，而且**刻意不用 canvas 的漸層物件** —— 註解說明理由是逐 column 繪製時每個 column 都會配置一個 gradient object。所以正確做法是分段實心色帶，不是真漸層。

（原始評估中用了「垂直漸層」這個詞，不精確；正確的實作形狀是分段色帶，而且這個 repo 已經替未來的實作者決定好了。）

實作範圍是 renderer 內部多塗兩筆：不需要 Blender、不需要新資產、不需要改 `RenderScene` 型別、不需要動任何 demo 內容。四個已知的咬人點見第六節。

### 可用：三層細節尺度 + 刻意留白

報告的 zoning 原則 —— primary masses / medium detail / fine greeble，且必須刻意保留乾淨的大面積，因為細節旁邊沒有空白就讀不出來，第一次把每個面塞滿 greeble 只會變雜訊。

拒馬已經有 rails + spikes 兩層，而且 `demo-scene.ts` 有一條「沒有東西高過 0.7」的規則（那是拋物線要能越過拒馬的高度上限）。那條規則本身就是 zoning。未來加細節時要記得它。

## 三、人物固定姿勢

現況已經比報告嚴謹：三張靜圖（normal / attack / hurt）是**從 atlas 裁出來的**，不是重渲，所以永遠不可能跟動畫第一幀不一致。這正是報告說的 single source of truth。

### 可用：auto-framing 相機

`build.py` 的 `ortho_scale = 2.5` 是手調的魔術數字。報告的做法是先算所有 mesh 的 world-space bounding box，再由半徑反推相機距離，好處是換一隻體型不同的角色不用重調，也不會不小心把相機放進模型裡。

目前只有一隻骷髏所以無所謂。一旦要第二隻，這個數字會開始漂。

### 可用，但判準必須換掉：adversarial critic loop

報告的 judge 比對的是 Starfield 截圖，直到判定達到同等水準才算完成。

這個 repo 已經手動跑過一輪同樣的東西。`build.py` 的 `configure_render` 有一段註解記錄：第一版 key light 開 620W 加高對比，把老骨頭打成接近白色，而「白色人形站在紫色火把地牢裡怎樣都像貼上去的」，最後降到 430W、exposure `-0.45`，理由是「renderer 會按 depth 和燈光把 sprite 壓暗變暖，所以烘焙的結果必須坐在它會被推進去的範圍之下，而不是頂端」。

關鍵差異：**judge 必須看遊戲內截圖，不能看 Blender render。** 因為「像貼上去的」這個缺陷在 Blender 裡根本不存在 —— 它只在 sprite 被合成進真實場景、真實尺寸、經過 runtime tint 之後才出現。這一點比報告的做法更嚴格，而且不能放寬。

## 四、人物骨架與動作

rig 和 10 段 action 都已經在 Blender 裡了。共用 kit 層也在。做第二隻人形的邊際成本是一個 build script，不是一條管線。

### 可用：variant

報告裡最有借鑑價值的具體案例是「四個 locker 看起來完全一樣」→ 拆成四個 variant，改門的開合狀態、輪廓、百葉、把手、損壞程度，各在場景裡用一次。

目前的敵人分兩類：史萊姆是 renderer 內程序化生成的 ring stack（squash / lean / wobble / droop，無骨架就能演出落地、撲擊、融化、劈半），骷髏是唯一有骨架的。appearance 種類只有 5 種史萊姆 + 骷髏 + placeholder。

同一組 rig 改 bone 長度、換武器、拿掉頭盔、少一隻手，共用同一組 action 只重渲，就能拿到新的敵人外觀。

### 但成本必須先算清楚（報告沒警告這件事）

一隻角色 = 10 clips × 8 方向 × 8 幀 = **640 次 render**，外加 10 張 2048×2048 atlas 進 repo。variant 是線性疊上去的。

而且這筆成本在 Three.js 之後會**整個消失**（見第五節第一條）。所以：

**若 Three.js 遷移在可見的時程內，不要現在擴 variant。** 那會是白丟的 640 次 render 和一批進了 repo 又要拔掉的二進位檔。

## 五、Three.js 之後可參考的地方

按價值排序。這一節是整份報告對這個專案最有用的部分。

**5.1 骷髏不要再烘 billboard，直接匯出 rigged GLB。**
rig 和 action 已經在 Blender 裡，匯出 armature + actions 幾乎免費。一次解決三件事：8 方向量化消失、鏡像持劍的 hack 消失、640 次 render 和 10 張 atlas 全部消失。**單筆收益最大。**

**5.2 幾何進 GLB，貼圖分開走 WebP。**
報告的理由與這裡的需求完全對上：albedo 保持接近白、只帶明暗調制，最終顏色由 material color 決定，所以換整層地牢配色不需要改任何一張貼圖。`src/presentation/procedural-textures.ts` 現在就是按 theme 換色在跑，無縫接。

**5.3 烘 transform 進 vertex、按材質合併。**
祭壇的八個 box、拒馬的 rails + spikes，會塌成一到兩個 draw call。報告的第二個理由同樣重要：合併後 shader 看到的是統一的 object-space position，接縫圖樣不會在每個零件邊界重新開始。

**5.4 Draco quantization。**
報告用 14-bit position 在 16 公尺船艙上得到約 1mm 誤差，GLB 從 16.3MB 降到 1.8MB。整層地牢約 30 cell 見方，容錯更寬鬆，設定可直接沿用。

**5.5 3×3 九宮格烘 tiling 貼圖。**
高模生成成九宮格、只烘中央那格，讓邊界的 AO 和光線看得到鄰居，因此能無縫重複、不需要 cross-fade。現在的牆是 64px 的 canvas 程序貼圖 —— **這條是視覺提升最大的一項**：磚縫、焊道、鉚釘從 64px 手繪變成真正的 tiling PBR set。

**5.6 AO 在組裝好的場景裡烘，不是單件孤立烘。**
報告的做法是每個 kit master 在烘 AO 前先放到它在遊戲裡的實際位置，鄰居只作為 occluder 不輸出。translate 到這裡就是：走廊／房間 kit 要帶著鄰接的牆一起烘。報告另外提到要把 AO 最低值抬到約 0.34，避免 AO 變成永遠無法被燈光救回的純黑貼痕 —— 這條值得照抄，火把是這個遊戲唯一的光源。

**5.7 remove doubles → bevel。**
報告稱這是「primitive 和 modelled part 最大的差別」：純 90 度邊緣不產生可見 highlight，加幾毫米倒角後每盞燈都會在邊緣形成亮線。做法是先用約 20 微米距離焊接重合頂點，再套 Bevel modifier，大型件約 3mm、一般 props 約 1.6–2.2mm、小物約 1mm。

骷髏正是報告說的 primitive soup（ellipsoid / cylinder / box / torus 各自獨立頂點）。

**但現在做沒有用。** 2 公尺角色烘進 256px 的 atlas cell，一個 pixel 約 8mm，2mm 倒角是四分之一像素。**這條的價值 100% 在模型直接進場景之後。**

**5.8 height-field → normal**（第一節推遲的那條）在這時候才用得上。

## 六、Three.js 之後的投影

這一節與外部報告無關，是從現有 renderer 反推出來的遷移錨點。它決定上面幾條能不能落地。

### 6.1 垂直 FOV 可以精確接上

renderer 的 `#planeLength()` 回傳 `width / (2 × height)`，而一 cell 的世界高度投影成 `canvasHeight / depth` 像素。

反推：半螢幕高（`canvasHeight / 2` 像素）對應的世界半高 H 滿足 `H × canvasHeight / depth = canvasHeight / 2`，得 `H = depth / 2`，所以：

```text
tan(halfFovY) = 0.5   →   fovY = 53.13°
```

Three.js `PerspectiveCamera(53.13, aspect, ...)` 在任何 aspect 下的水平半寬都是 `0.5 × aspect`，與 `#planeLength()` 完全相同。**視野可以做到零手感差異，這是可驗證的數字，不是估計。**

一個小尾巴：`#horizon` 用的是 `height × 0.49` 而不是 `0.5`。相機打平會讓地平線上移約 1%，要完全一致得補一點 pitch。

### 6.2 pitch 的手感會變，而且會變好，但要重測

現在的 pitch 是**地平線剪切**，不是真旋轉 —— column raycaster 只能做到這個（renderer 註解自己說了：columns 保持垂直，所以往上看是整個投影往下滑）。Three.js 給的是真旋轉。任何按剪切調過的內容（自由視角低頭時看得到什麼）都要重看一次。

### 6.3 cell ↔ 公尺的常數目前不一致，Three.js 會立刻放大它

推算過程（數值來自 2026-07-30 的程式碼）：

| 來源                     | 值                         |
| ------------------------ | -------------------------- |
| 骷髏 Blender 模型高度    | 2.08 m                     |
| `SKELETON_DISPLAY_SCALE` | 1.16 cell（整張圖的高度）  |
| Blender `ortho_scale`    | 2.5（人形佔畫面 2.08/2.5） |
| 人形實際佔畫面           | 約 0.97 cell               |
| `DEMO_WALL_HEIGHT`       | 1 cell                     |
| `eyeHeight`              | 0.5 cell                   |

得出 **1 cell ≈ 2.14 m**。骷髏差不多正好頂到天花板，這部分是對的。

但眼睛在 0.5 cell ≈ **1.07 m** —— 現在是用大約腰部的高度在看一個兩公尺的骷髏。這是 raycaster「眼睛在牆高一半」的老慣例，billboard 吸收得掉（`verticalAnchor` 和 `displayScale` 就是在吸收它），**mesh 吸收不掉**。

**所以遷移前應該先定死「一 cell 等於幾公尺」，再把 eye height 改成人的高度。** 這正是報告 `M = 0.001` 那條的精神：先把單位定死，再開始建模。

### 6.4 painter's algorithm 的已知破口會自動消失

renderer 註解記錄：sprite 和 box 一起深度排序，唯一失效的情況是「sprite 站在 box 裡面」，而目前的幾何不會產生這種情形。真 depth buffer 免費解掉。

### 6.5 其他對應

`RENDER_SCALE = 0.55` → `renderer.setPixelRatio`；`MAX_DEPTH = 18` → far plane 與 fog 距離。

## 七、兩個原本評估為「立即可做」的項目

這兩項在原始評估裡標為「現在」，成本極低。**依決議一併延到 Three.js refactor。** 內容完整保留，因為它們在遷移後仍然有效，只是形式會變。

### 7.1 Box 面的接觸陰影

**問題**：祭壇、拒馬、樓梯門框的每個面都是一整片同一個顏色，讀起來像立起來的紙板而不是放在地上的物件。人眼對「物件與地面夾角那一圈的暗」極度敏感，那是它「坐」在地上而不是「浮」在地上的訊號。

**先例**：牆已經有這個處理（見第二節），做法是底部約 18% 高度兩條實心橫帶、上淡下深、用查表好的 shadow style 避免每次拼字串、**不用 gradient object**。

**四個咬人點**（實作時必須先想清楚）：

**(a) 只有側面要，頂面不要。** 頂面在世界裡是水平的，沒有「上緣下緣」可言，它在螢幕上的上下只是透視。對頂面補暗帶會變成一條莫名其妙的髒痕。現有程式碼已經用一個負的 shade 值標記頂面，可以直接判斷。

**(b) 快速路徑也要處理。** `#fillProjectedQuad` 有一條 fast path：整個面都比所有牆近、不會被切時，用一次 path fill 取代逐 column 迴圈（註解說站在出口平台前會同時出現好幾個又近又寬的面）。暗帶必須兩條路徑都補，否則會出現「站遠有接觸陰影、走近就消失」的閃爍 —— **那比沒有還糟**。

**(c) 疊起來的 box 要站在它下面那個東西上，不是站在地板上。** 現有的 box 大量是堆疊的：

| box           | bottom        | 實際站在   |
| ------------- | ------------- | ---------- |
| `altar-base`  | 0             | 地板       |
| `altar-shaft` | 0.16          | 祭壇底座上 |
| 拒馬 spike    | 鐵軌頂        | 鐵軌上     |
| `exit-lintel` | 1.05          | 兩根門柱上 |
| 樓梯 step     | `step × 0.11` | 前一階上   |

若判斷條件寫成「z 接近 0 才加暗帶」，shaft、spike、lintel 全部拿不到，底座暗而上面那截均勻亮，接縫反而更明顯 —— 適得其反。

正確做法是**每個 box 用自己那個面的下緣**，不查 z。同時更簡單也更對：東西本來就該被它所站立的東西襯出陰影。

**(d) 有一個是浮空的，要親眼確認。** `exit-post` 的 bottom 是 0.33。若它下面真的什麼都沒有，加暗帶會憑空多出一圈陰影。這不值得寫規則去偵測 —— 跑一次走到出口看一眼就知道要不要特例。

**明確不做的更完整版本**：真正的接觸陰影還有另一半，box 周圍的地板也該變暗。但地板是在另一個 pass 裡逐 pixel 畫的，要加就得在最熱的迴圈裡多查一次「附近有沒有 box」，成本高一個數量級，收益是遞減的第二筆。牆的做法就只有自己那一側、沒有畫到地板上，效果已經足夠說服當初寫它的人。

**遷移後的形式**：Three.js 有真正的 AO（貼圖或 SSAO），這一項會被 5.6 取代 —— 但取代它的前提是 5.6 真的做了。若 Three.js 版先上、AO 還沒烘，這個問題會原封不動地重新出現，而且在真 3D 裡更明顯。

### 7.2 Handedness convention 收進 primitives.py

**兩套座標系對「右邊是哪邊」的看法不一樣。**

- **遊戲**：格子座標，x 往右、y 往下（螢幕式、地圖式）。從投影數學反推：相機朝 +X 時，世界 +Y 出現在**螢幕右邊**。
- **Blender**：標準右手系、Z 軸朝上。相機朝 +X、頭頂 +Z 時，世界 +Y 在**左邊**。

兩邊差一個鏡射。老實把遊戲角度抄到 Blender 相機上，烘出來的每一張圖都是遊戲期待的鏡像。

**為什麼特別陰險：在正面看不出來。** 骷髏大致左右對稱，所以方向 0（正面）和方向 4（背面）鏡射等於沒鏡射，完全正常；只有兩個側面會把「朝左走」變成「朝右走」。畫面上是腳往一邊、身體朝另一邊的骷髏。

**最貴的地方不是難修，是會被誤診。** 看到走路怪，第一直覺是查 walk cycle 的 keyframe、查取幀邏輯、查 AI 給的 facing 角度 —— 而錯的是相機擺放。

**現在的修法**：把方向盤反轉（`π/2 - (d/N)·2π`，原本應是加號），把相機放到「那一列的觀察者在遊戲空間實際站的位置」。代價寫在註解裡而且很誠實：**鏡射不是旋轉，沒辦法用轉的把鏡像轉回來**，所以每一列各自對，但整隻骷髏是鏡像的。所有 clip 一起鏡射，姿勢彼此一致，不會穿幫。

**問題在存放位置。** 這個知識目前散在三個互不相識的地方：

1. `build.py` 的十幾行註解 —— 完整推導
2. 同一個檔案裡的一個負號 —— 實際生效的東西
3. `src/demo/demo-scene.ts` 的 `skeletonDirection`，runtime 用「觀察者角度 − 朝向角度」反推該取哪一列 —— **合約的另一半，寫在另一個語言的另一個檔案裡**

而 `dev/tools/blender-kit/primitives.py` —— 那個號稱「every offline model this project bakes」的共用 kit —— 對這件事一無所知。

下一個要烘第二隻角色、或任何有正面的道具（門、旗、雕像、寶箱、有把手的箱子）的人，會從 primitives.py 開始，看不到那些註解。他會寫下最自然的加號，Blender 預覽正常、遊戲正面正常、側面錯 —— 然後去查別的地方。**同一個 bug 會被重新踩、重新誤診。**

**要搬的三件事**（不是新功能，是搬家）：

1. **一個有名字的函式**。把相機擺放整段（角度計算、location、look_at、連同 key/fill 燈的相對擺位）變成 primitives.py 裡的一個具名函式。負號活在裡面，不在呼叫端。呼叫端只說「我要第 d 個方向」。
2. **說明跟著搬，但壓縮成三句**：遊戲格子相對 Blender 是左手系 → 方向盤要倒著轉 → **烘出來的成品是刻意鏡射的，不要試圖修正它**。第三句最重要 —— 下一個看到鏡像成品的人很可能會覺得那是 bug 而去「修好」它，一修就把兩個側面弄反，而且他會覺得自己在修 bug。這種註解的價值不是解釋，是防止善意的破壞。
3. **把合約明文寫出來**：「第 d 列 = 觀察者站在距離模型朝向 d/N 圈的位置，角度在遊戲空間量測。」有這一句，任何人拿到新資產可以直接對照 runtime 那半邊檢查，不用重新推導投影數學。

**附帶一個很划算的小東西：非對稱測試件。** 這整類 bug 的共同特徵是在對稱物體上完全隱形。kit 裡值得放一個刻意不對稱的測試模型（右肩塗一塊色就夠），烘出 8 個方向、眼睛掃一次繞轉方向。三十秒的檢查，擋掉一個會被誤診成動畫問題的 bug。比註解可靠，因為註解會被跳過，圖不會。

**這個 hack 什麼時候會不再夠用**：角色有不對稱裝備（左盾右劍、單邊護肩、腰間掛袋）、資產上有可讀的字或紋章、或有方向性的機構（門把、齒輪、旋轉方向）。

**遷移後的形式**：骷髏變成場景裡真正的 rigged GLB 之後，鏡射 hack 整個消失（不再有烘焙方向這回事）。但 convention 更需要存在 —— 那時候座標轉換會集中到「匯入」這一個點上，更應該有名字、只寫一次。報告裡船艙那套用關掉 Y-up 轉換讓 Blender 座標直接等於遊戲座標、寧可讓 viewport 看起來躺著，走的就是這條路。

## 八、決議與順序

**全部延到 Three.js refactor 時一併處理。**

原始評估把 7.1 和 7.2 標為「現在做」，理由是成本極低。這個決議推翻了那個排序，理由是：

- 7.1 在 Three.js 之後會被真 AO（5.6）取代，現在做等於做一份會被丟掉的近似
- 7.2 的具體形式（相機擺放函式）在 Three.js 之後會變成匯入座標轉換，搬家的目的地不一樣
- 兩項都不是 bug 修復，是品質提升，沒有理由在架構將變的前夕分兩次做
- 更重要的是第四節的成本結論：**任何在遷移前擴充烘焙資產的動作都是白丟的**，而這兩項都是為了服務烘焙管線
