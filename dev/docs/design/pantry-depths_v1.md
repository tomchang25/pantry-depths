## 一、設計定位

### 核心概念

玩家以格子為單位在五層地牢中前進，只能前進與轉向，不能後退。敵人固定不動，不追擊也不尋路，它們是站在路上的數值關卡。玩家攻擊一次，敵人若還活著就反擊一次，因此通過成本在接觸前就完全可以心算。

三種顏色的鑰匙控制兩件事：紅色是路，藍色是攻擊，黃色是防禦。玩家用生命買到鑰匙，用鑰匙買到數值，再用數值讓後面的路變便宜。第四層的三岔房間是這條線的收束點——直走向下，左轉攻擊，右轉防禦。

第五層的終點是公主。打倒她之後，牢門打開，被囚禁的魔王走出來，遊戲結束。

### 舞台

某座宅邸底下的五層儲藏窖。玩家從最上層的酒窖一路往下，經過冰窖、肉窖與守衛層，最深處是一間上了鎖的儲物間。

越往下越不像儲藏室。這個尺度是刻意的：玩家花了三十分鐘穿過人家的地窖，只為了把一隻魔王從儲物間裡放出來。

遊戲的主要決策是：

- 這隻敵人現在值不值得打，還是先去拿升級再回來。
- 為了一把鑰匙付出的生命，能不能被它帶來的數值賺回來。
- 現在的攻擊力打不打得動前面那隻，還是根本穿不透。
- 進入公主房之前，剩下的生命夠不夠。

### 一句話定位

> 在無法後退的地牢裡，用生命買數值，再用數值買回生命。

### V1 系統

| 系統             | 主要作用                                           |
| ---------------- | -------------------------------------------------- |
| Grid Movement    | 格子前進、90 度轉向、禁止後退                      |
| Adjacency 反擊   | 玩家每次行動後，所有相鄰存活敵人各攻擊一次         |
| Combat           | 雙向 `攻擊 − 防禦`，下限 0                         |
| Stat Progression | 攻擊與防禦只透過藍門與黃門成長，共四次             |
| Key and Door     | 紅色開路、藍色加攻擊、黃色加防禦                   |
| Breakable Wall   | 沿用 Combat 判定的可破壞牆                         |
| Hot Spring       | 隱藏彩蛋，無限次補滿生命；同時是 debug 工具        |
| Floor Transition | 雙向樓梯，五層固定地圖                             |
| Renderer         | Raycasting 假 3D、程序化貼圖、火把光照與程序化音效 |

### Frozen extensions

以下內容不屬於 V1，也不建立 runtime placeholder：

- 裝備、武器切換、可選升級路線
- 經驗值、等級、擊殺獎勵、商店、金幣
- 藥水、寶箱、背包格、可攜帶道具
- 敵人移動、追擊、尋路、特殊能力、狀態異常
- 存檔、讀檔、關卡選擇、難度選擇
- 第六層、真魔王戰、多結局
- Runtime 程序生成

原本 prototype 中的金幣、寶箱、藥水與背包格全部移除。攻擊與防禦的唯一來源是四扇門，沒有任何其他成長管道。

### 設計邊界

- 玩家的攻擊與防禦只會在開門的瞬間改變，一共四次。
- 敵人永遠不移動、不轉向、不選擇目標。
- 沒有任何隨機數影響戰鬥結果。
- 沒有擊殺獎勵，所以打怪永遠是純支出。
- 地圖在開發期生成一次後烘焙成固定資料，遊戲中不生成。
- 沒有存檔；死亡即整局重來。預期單局 12–18 分鐘。

## 二、核心循環

### 單層循環

```text
從樓梯口進入本層
→ 前進、轉向、探索走廊
→ 遇到敵人，讀取 HP／攻擊／防禦，計算通過成本
→ 決定戰鬥、繞路，或先去拿升級再回來
→ 找到鑰匙
→ 回頭開啟對應顏色的門
→ 取得數值或通路
→ 找到往下的樓梯
```

### 全局循環

```text
B1：學會操作，發現隱藏牆
→ B2：藍門給第一次攻擊提升，骷髏從 24 變成 12
→ B3：黃門給第一次防禦提升，蝙蝠開始完全免傷
→ B4：三岔房間一次拿到攻擊 +5 與防禦 +4
→ B5：守衛變成 8 點小事，公主是最後一筆 40
→ 牢門開啟，魔王走出
→ 結局
```

### 死亡

```text
生命歸零
→ 顯示到達層數、最終攻擊防禦、已開啟門數
→ 一鍵重新開始整局
```

不保留任何進度。所有數字對玩家可見，死亡永遠是規劃錯誤而不是運氣。單局長度短到重來不算懲罰。

## 三、世界結構

### 名詞

| 名詞     | 定義                                   |
| -------- | -------------------------------------- |
| Floor    | 一張固定的格子地圖                     |
| Cell     | 最小單位；玩家永遠站在某個 Cell 的中心 |
| Facing   | 玩家朝向，只有北、東、南、西           |
| Adjacent | 與玩家共邊的四個 Cell，不含對角線      |
| Action   | 一次會觸發敵人反擊結算的玩家輸入       |
| Stage    | 玩家目前的攻擊／防禦組合，共五種       |

### 五層結構

B1 最靠近地面，B5 最深。玩家一路往下。

| Floor | 尺寸  | 主題         | 本層新增                              |
| ----- | ----- | ------------ | ------------------------------------- |
| B1    | 11×11 | 酒窖         | 紅鑰匙 #1、紅門 #1、隱藏牆、溫泉      |
| B2    | 13×13 | 冰窖         | 藍鑰匙 #1、藍門（攻擊 +2）            |
| B3    | 13×13 | 肉窖         | 黃鑰匙 #1、藍鑰匙 #2、黃門（防禦 +2） |
| B4    | 15×15 | 守衛層       | 紅鑰匙 #2、黃鑰匙 #2、三岔大房間      |
| B5    | 11×11 | 最深的儲物間 | 紅門 #2 之後的最終路線、公主、牢房    |

主題只影響材質配色與裝飾物，不影響任何規則。肉窖的骨堆、冰窖的濕痕、酒窖的木桶都是純裝飾，沿用同一套程序化材質換色即可。

樓梯雙向可用。玩家隨時可以回到已探索的上層，這是溫泉彩蛋與「先升級再回頭」路線的前提。

## 四、操作

### 輸入表

| 輸入 | 行為                                     | 觸發反擊 |
| ---- | ---------------------------------------- | -------- |
| W    | 前方是地板則前進；是敵人或可破壞牆則攻擊 | 是       |
| A    | 左轉 90 度                               | 是       |
| D    | 右轉 90 度                               | 是       |
| S    | 無效果，只播放拒絕 feedback              | 否       |
| E    | 與正前方的門、樓梯、溫泉互動             | 是       |

滑鼠不參與遊戲。取消 pointer lock 與自由視角。

### 為什麼不能後退

不能後退會產生一條免費的規則：一旦貼到敵人面前，撤退要付兩次轉向的代價。

```text
撤退成本 = 2 × max(0, 敵人攻擊 − 玩家防禦)
```

前期對地精是 8，對骷髏是 12；拿到黃門（大）之後對這兩者都是 0。撤退成本自己就會隨進度崩塌，不需要另外設計。

### S 的 feedback

- 畫面向後微晃約 6 px 後彈回，角色不移動
- 播放低頻鎖鏈聲
- 火把光短暫收縮
- 螢幕下緣淡出文字：`地城不允許你後退`

文字整局最多顯示三次，之後只保留晃動與音效。

### 動畫時序

| 行動 | 時長  | 說明                                  |
| ---- | ----- | ------------------------------------- |
| 前進 | 0.22s | 位置線性補間，帶步行晃動              |
| 轉向 | 0.18s | 角度 ease-in-out 補間                 |
| 攻擊 | 0.32s | 沿用 prototype 的 `sin(0→π)` 揮刀曲線 |

補間期間鎖定輸入，只緩衝最後一個按鍵。反擊在補間開始時就結算完成，動畫只是表現。

## 五、戰鬥

### 傷害公式

雙向使用同一條公式：

```text
造成傷害 = max(0, 攻擊方攻擊 − 受擊方防禦)
```

推導出的成本模型：

```text
擊殺所需回合 = ceil(敵人HP / (玩家攻擊 − 敵人防禦))
每回合受傷   = max(0, 敵人攻擊 − 玩家防禦)
擊殺成本     = (擊殺所需回合 − 1) × 每回合受傷
```

兩個下限狀況都是遊戲的一部分：

- **玩家攻擊 ≤ 敵人防禦**：刀彈開，敵人 HP 不變，不顯示傷害數字，畫面顯示 `無法穿透`。這是「回去開藍門」的訊號。這仍然算一次 Action，敵人照常反擊。
- **敵人攻擊 ≤ 玩家防禦**：不扣血，播放 Block 特效與藍色外框 VFX，短促金屬音。這是防禦升級的即時回饋。

### 結算順序

```text
玩家輸入一個 Action
→ 解析 Action（移動／轉向／攻擊／互動）
→ 若為攻擊，對正前方套用 max(0, 玩家攻擊 − 目標防禦)
→ 移除 HP 歸零的敵人
→ 以行動結束時的位置，掃描四個相鄰 Cell
→ 每個存活敵人各造成一次 max(0, 敵人攻擊 − 玩家防禦)
→ 若玩家 HP ≤ 0，進入死亡流程
```

- 反擊以行動「之後」的位置判定。
- 被殺死的敵人不反擊。
- 對角線不算相鄰。
- 相鄰兩隻敵人就是每回合被打兩次，不需要新機制。
- 玩家攻擊只作用於正前方一格。
- 門與牆是不可通行 Cell，隔著它們不算相鄰。

### Worked Example

玩家 ATK 5、DEF 0，正前方是骷髏（HP 10、ATK 6、DEF 1），生命 96：

每刀造成 `5 − 1 = 4`，需要 `ceil(10 / 4) = 3` 回合；每回合受 `6 − 0 = 6`。

| 回合 | 骷髏 HP | 反擊 | 玩家 HP |
| ---- | ------: | ---: | ------: |
| 1    |       6 |   −6 |      90 |
| 2    |       2 |   −6 |      84 |
| 3    |       0 |    — |      84 |

成本 12 = `(3 − 1) × 6`。

同一隻骷髏在不同 Stage 的價格：

| 玩家狀態   | 每刀 | 回合 | 每回合受傷 | 成本 |
| ---------- | ---: | ---: | ---------: | ---: |
| ATK3 DEF0  |    2 |    5 |          6 |   24 |
| ATK5 DEF0  |    4 |    3 |          6 |   12 |
| ATK5 DEF2  |    4 |    3 |          4 |    8 |
| ATK10 DEF2 |    9 |    2 |          4 |    4 |
| ATK10 DEF6 |    9 |    2 |          0 |    0 |

同一隻怪從 24 掉到 0。玩家會非常清楚地感覺到每一扇門的價值。

### 外觀

敵人使用**固定的 512×512 sprite 圖檔**，不再沿用 prototype 的 runtime 程序化繪製。五種敵人都採同一個史萊姆造型，以 offline-baked 綠、黃、藍、紅、紫區分 gameplay archetype；牆面、地板與天花板維持程序化材質。

#### 為什麼是 512

`RENDER_SCALE = 0.55`、內部解析度上限約 1050×650，sprite 的螢幕高度是 `內部高度 ÷ 距離`：

| 距離         | 螢幕高度      | 相對 512  |
| ------------ | ------------- | --------- |
| 1 格（貼臉） | 約 500–650 px | 約 1:1    |
| 2 格         | 約 250–325 px | 降採樣 2× |
| 3 格         | 約 165–215 px | 降採樣 3× |

512 在貼臉時剛好是原尺寸，不會放大糊掉；其餘距離都是降採樣，安全。但玩家大部分時間看到的是 200–320 px，畫面之後還會被 CSS 從 0.55 再放大一次，等於兩次重採樣。

#### 作畫規格

- 描邊在 512 尺度下要 **8–12 px**，不是 2–3 px。
- 大色塊、高對比，細線條與小圖案在降採樣後會消失。
- 史萊姆輪廓在純黑走廊裡仍要清楚；五種 gameplay archetype 由離線烘焙的顏色、顯示尺寸與浮空位置區分。
- **平光、中性打光。** 不在圖裡烘進光源方向與陰影。
- 每張都畫滿整個 512 框、腳底貼下緣，尺寸由資料控制而不是由圖控制。

一般、攻擊、受擊三張綠色史萊姆母版必須共用一份 style spec（描邊粗細、輪廓規則、平光要求），再 offline bake 成五色獨立 PNG。Runtime 分別載入十五張圖片，不從共用來源即時改色。它們要在暗紫地牢背景上被暖橘火把照亮，配色以 prototype 現有的調色盤為錨。

#### Sprite 記錄

512×512 的框對蝙蝠和對公主一樣大，所以尺寸必須由資料決定：

```text
Sprite
├── normalImage: 512×512 PNG（含 alpha）
├── attackImage: 512×512 PNG（含 alpha）
├── hurtImage: 512×512 PNG（含 alpha）
├── scale: 相對於格高的顯示倍率
└── anchorY: 垂直偏移，0 為腳底貼地，負值為浮空
```

| 敵人 | 顏色 | scale | anchorY | 備註       |
| ---- | ---- | ----: | ------: | ---------- |
| 蝙蝠 | 綠   |  0.40 |   −0.25 | 浮空史萊姆 |
| 地精 | 黃   |  0.70 |       0 |            |
| 骷髏 | 藍   |  0.85 |       0 |            |
| 守衛 | 紅   |  1.05 |       0 |            |
| 公主 | 紫   |  1.30 |       0 | 最大史萊姆 |

調整敵人大小是改 `scale`，不是重出圖。

#### 光照

現行 prototype 的 sprite 只做 depth buffer 遮蔽與 `globalAlpha` 淡出，**沒有距離 tint**。程序化 sprite 用暗色調色盤所以看不出來，但換成正常打光的圖檔後，遠處敵人會在紫黑走廊裡發亮，像貼上去的。

因此換圖的同時必須讓 sprite 套用與牆面相同的距離衰減與暖色火把加成。這也是素材必須平光的原因：圖自帶光影會與 runtime 光照互相打架。

#### 受擊表現

sprite 是逐欄 2 px 切片繪製的，一隻敵人一幀就是 150–300 次 `drawImage`。因此受擊閃白**不能用 `ctx.filter`**，那會變成每幀數百次濾鏡重建。

受擊時先切換成 offline-baked hurt image，再由 presentation 依該圖片 alpha 產生短暫的 depth-aware 白色 silhouette。白閃是 event-time VFX，不是額外 runtime color variant，也不能在逐片 draw loop 裡使用 `ctx.filter`。

敵人死亡沿用 hurt image，由 presentation 把它切成左右兩片後向外墜落並淡出；公主遵守相同規則。

#### 不做

- **不做 frame-by-frame 動畫。** 每個顏色只有 normal、attack、hurt 三個 semantic states；裝飾性浮動與死亡位移由 presentation timing 實現。
- **不做 sprite sheet、atlas packer 或 runtime recoloring。** 十五張敵人 PNG 各自載入。
- **不把牆面材質也換成圖檔。** 程序化在那裡是正確的。

公主使用最大的紫色史萊姆立繪與較重的死亡 VFX，但遵守完全相同的圖片狀態與公式。她沒有二階段、召喚、法術或場地攻擊。

## 八、鑰匙與門

三種顏色各 2 把鑰匙、2 扇門，位置固定。鑰匙以顏色計數持有，不區分個體。

### 顏色語意

| 顏色 | 語意 |
| ---- | ---- |
| 紅   | 通路 |
| 藍   | 攻擊 |
| 黃   | 防禦 |

顏色語意全局一致，玩家看到門的顏色就知道背後是什麼。

### 配置

| 顏色 | 鑰匙位置    | 門位置              | 門後           |
| ---- | ----------- | ------------------- | -------------- |
| 紅   | B1、B4 前段 | B1 通往 B2 的樓梯前 | 通路           |
|      |             | B4 大房間，直走     | 通往 B5 的樓梯 |
| 藍   | B2、B3      | B2                  | 攻擊 +2        |
|      |             | B4 大房間，左轉     | 攻擊 +5        |
| 黃   | B3、B4 前段 | B3                  | 防禦 +2        |
|      |             | B4 大房間，右轉     | 防禦 +4        |

### B4 三岔大房間

玩家從 B4 前段拿到紅鑰匙 #2 與黃鑰匙 #2，帶著 B3 拿到的藍鑰匙 #2 進入一個開闊的高天花板房間。正對面三扇門並排，顏色明確：

```text
        [藍門] [紅門] [黃門]
          ↑      ↑      ↑
        攻擊+5  向下  防禦+4
                  ↑
              玩家進入
```

這不是二選一，備齊鑰匙就能全開。它是整局的收束畫面：玩家在這裡一次拿到全部剩餘成長，然後推開中間的紅門往下。

真正的選擇發生在上游——那三把鑰匙都要付生命才能拿到。

### 互動

面向門按 E：

- 持有對應鑰匙：鑰匙 −1，門開啟並永久成為可通行 Cell。升級門額外播放數值提升演出（HUD 數字跳動、全螢幕色閃、專屬音效）。
- 未持有：門不動，播放沉重鎖聲，HUD 閃爍該顏色的鑰匙圖示。

開門是一次 Action，會觸發相鄰敵人反擊。門在 minimap 上以對應顏色顯示，已開啟的改為暗色輪廓。

## 九、隱藏牆與溫泉

這是全遊戲唯一的秘密，只出現在 B1。

### 隱藏牆

隱藏牆重用 Combat 判定，把牆當成一個不會反擊的敵人：

```text
BreakableWall
├── cell
├── hp: 6
├── atk: 0
└── def: 0
```

HP 6 表示 Stage 0（攻擊 3）要兩刀，後期一刀。每次命中：

- 裂痕貼圖進入下一階段
- 掉落石屑粒子
- 播放帶低頻的碎石聲
- 鏡頭輕微震動
- 從裂縫漏出暖橘色光

普通牆被攻擊只有悶響、刀反彈與火把晃動，不產生裂痕、不掉粒子、不漏光。這個差異必須非常明顯，否則玩家會開始對每一面牆按 W。

### 提示

- 磚塊排列與周圍不同
- 有一條貫穿的細裂縫
- 火光照上去會漏出一點暖色
- 地面有水漬
- 靠近兩格內能聽到微弱水聲

全遊戲只有這一面隱藏牆。不要為了「公平」再加第二面。

The breakable wall uses directional hint metadata rather than separate one-way and two-way wall types. `hintFaces` names the wall faces whose material exposes the crack, warm light, and other authored clues. A face name is its outward cardinal normal: `north` is the face seen from the cell north of the wall. Every face remains attackable, all faces share one health value, and destroying the entity opens the cell from every direction.

### 溫泉

牆後是一個小房間，色調從紫黑地牢切換成暖橘與蒸氣。面向水面按 E：生命補滿。**無使用次數限制，永久有效。**

溫泉的定位是彩蛋與 debug 工具，不是資源管理系統：

- 它藏在 B1，也就是最靠近地面的那一層。任何一趟補血都要從當前深度一路爬回最上層再走下來。距離本身就是成本。
- 找到它的玩家得到的是「這局不太可能失敗」，這是對探索的獎勵，不是通關條件。
- 開發期可以直接把玩家丟到任何樓層測試，回 B1 補滿即可重跑，不需要另外做 debug 面板或無敵指令。

**已知後果：** 找到溫泉之後，玩家可以用來回跑的時間換取任意多的生命。這是刻意接受的，因為「發現秘密後遊戲變簡單」本身就是彩蛋該有的樣子。它對最終路線壓力與恢復節奏的影響由 playable presentation 的人工試玩判斷，不從預設生命預算推導。

## 十、生命與路線體驗

最大生命 120，全局不成長；溫泉是可重複使用的隱藏恢復點。最終五層不預先指定必經路線成本、通關剩餘生命、個別敵人成本比例或其他數值門檻。

### 必經路線

Final Floor Design 在 playable presentation 中反覆走完整路線，人工判斷壓力、犯錯空間、恢復節奏、遭遇密度與終局感。結構驗證、deterministic replay 與 balance report 用來確認路線合法並描述當前 content 的實際結果；它們不替人工試玩設定合格數字。

### 升級的必要性

| 略過的門      | 後果                                                       |
| ------------- | ---------------------------------------------------------- |
| B2 藍門       | 玩家攻擊成長較慢，後續敵人需要更多次攻擊。                 |
| B3 黃門       | 玩家承受較高反擊壓力。                                     |
| B4 藍門（大） | 玩家無法穿透公主防禦，是唯一固定的硬性進度要求。           |
| B4 黃門（大） | 玩家承受較高終局壓力；是否值得開門由實際路線體驗自然呈現。 |

結論很乾淨：**攻擊決定你打不打得動，防禦決定你付多少。** 只有一扇門是硬性必須，其餘都是安全邊際。這條規律玩家玩一次就懂，也讓所有升級都有明確的動機差異。

### 選擇性內容

The final optional-enemy placements are selected during the final floor-content pass after topology validation and route-report tooling exist. B3 does not contain the previously proposed pair of optional high-cost Guards.

## 十一、地圖生成與烘焙

「程序生成後固定」的正確實作是離線 pipeline，不是 runtime 生成器。

### 流程

```text
Build a rough development-only maze generator that never enters the game
→ Generate any positive floor count from an explicit seed
→ Export candidate JSON and validate one concrete structural solution
→ Commit a provisional five-floor set for pipeline, viewer, and replay-tool development
→ Manually adjust stairs, keys, doors, enemies, breakable walls, hot springs, dead ends, and landmarks
→ Revalidate the edited JSON without regenerating it
→ Use route replay and balance evidence to select the final V1 five-floor content
→ Keep the committed JSON as runtime authority; the game always loads fixed maps
```

生成器不進 build。遊戲本體沒有任何迷宮生成程式碼。

一旦改成 runtime 生成，就必須額外處理：鑰匙是否生成在自己的門後、必經傷害是否超過最大生命、玩家是否可能在攻擊不足時被鎖在守衛後面、B4 三岔房間的幾何是否成立、隱藏房是否破壞連通性、生成失敗如何重試。這套驗證框架的成本遠高於遊戲本身，而且對玩家完全不可見。

### 地圖資料格式

```text
Floor
├── size: { w, h }
├── tiles: string[]        // 每字元一格
├── entry: { x, y, facing }
├── stairs: { id, cell, destinationStairId, arrivalFacing }[]
├── enemies: Enemy[]
├── keys: { color, cell }[]
├── doors: { color, cell, effect, opened: false }[]
└── specials: BreakableWall[] | HotSpring[]
```

`effect` 只有三種：`passage`、`atk: +n`、`def: +n`。

Tile characters describe only static environment geometry and material. Interactive or stateful objects remain separate entity records.

| 字元 | 意義                 |
| ---- | -------------------- |
| `.`  | Passable floor       |
| `#`  | Solid stone wall     |
| `=`  | Solid old brick wall |
| `+`  | Solid iron-bar wall  |

Doors, keys, enemies, stairs, hot springs, and breakable walls are separate records so they can move without rewriting base terrain. A breakable wall overlays a floor tile and owns its cell, combat values, and directional hint faces; it is not a permanent solid tile, because its underlying cell becomes passable after destruction. The player-facing minimap treats an active breakable wall as an ordinary wall and does not reveal directional hints.

Presentation-only floor annotations such as wall torches, steam emitters, ambient lights, and wall-mounted decorations are deferred to the dedicated environment-feature slice. They are authored with floor content but do not become gameplay entities merely to reach the renderer.

## 十二、資訊透明

所有戰鬥數字對玩家可見。這是數值規劃遊戲，不是記憶遊戲。

### 面向敵人時

HUD 中央下方顯示：

```text
骷髏
HP 10 / 10
攻擊 6    防禦 1
```

不顯示「預計損失」。玩家自己心算 `ceil(10 / (5−1)) − 1) × (6−0)` 是遊戲的一部分，但原始數字必須全給。

穿不透時，敵人面板的防禦數字轉為紅色並加註 `你的攻擊無法穿透`。

### 常駐 HUD

| 元素    | 內容                    |
| ------- | ----------------------- |
| 生命    | 數字 + 血條，`96 / 120` |
| 攻擊    | 數字，升級時跳動        |
| 防禦    | 數字，升級時跳動        |
| 鑰匙    | 三個顏色圖示 + 持有數量 |
| 樓層    | `B3`                    |
| Minimap | 190×225，只畫已探索格   |

沿用 prototype 的探索迷霧：玩家周圍兩格半標記為 discovered。門、樓梯與已見過的敵人在 minimap 上以固定顏色標示。

### 戰鬥回饋

| 情況               | 表現                                                       |
| ------------------ | ---------------------------------------------------------- |
| 正常命中           | 敵人切換 hurt sprite、疊動態白閃 VFX、傷害數字彈出、打擊音 |
| 玩家穿不透         | 刀彈開動畫、火花、金屬高頻音、`無法穿透` 文字              |
| 玩家受傷           | 鏡頭震動、紅色 radial flash、低頻撞擊音                    |
| 玩家 Block（免傷） | 藍色外框 VFX、短促金屬彈開音、無震動、無紅色 flash         |
| 敵人死亡           | Hurt sprite 切成兩片墜落淡出、低頻收尾音                   |

Block 的藍框必須明顯到玩家在拿到黃門之後立刻注意到「這隻怪打不到我了」。這是防禦升級唯一的即時回饋管道。

### 側面威脅提示

第一人稱視角下，被看不見的側面敵人打會像 bug。相鄰敵人不在視野內時：

- 對應螢幕邊緣閃一道紅色刀光（Block 時改為藍色）
- 播放帶方向的短促喘息聲
- Minimap 上該敵人圖示脈動一次

## 十四、表現層

渲染架構完全沿用現有 prototype，不重寫。

| 項目     | 作法                                                           |
| -------- | -------------------------------------------------------------- |
| 3D       | Canvas 2D 的 DDA raycasting，逐欄 depth buffer                 |
| 地板天花 | Floor casting，逐 scanline 透視取樣                            |
| Sprite   | Billboard + depth buffer 遮蔽；來源為固定的 512×512 PNG        |
| 環境材質 | 啟動時以隱藏 Canvas 程序化繪製，無圖檔                         |
| 光照     | 距離衰減 + 暖色火把加成 + 牆面朝向明暗差 + screen-space glow   |
| 氛圍     | 紫色距離霧、暗角、餘燼粒子、film grain                         |
| 手部     | 固定圖片 view model：左手火把、右手長劍，Canvas transform 攻擊 |
| HUD      | DOM overlay，非 Canvas 文字                                    |
| Minimap  | 獨立的小 Canvas                                                |
| 音效     | Web Audio 即時合成，無音檔                                     |

材質與角色的分工是固定的：**環境用程序化，角色用圖檔**。牆面、地板、天花板需要可平鋪並經過透視取樣，程序化在那裡更省也更一致；角色需要剪影辨識度，圖檔才做得到。

HUD 用 DOM 而不是畫進 Canvas，理由有三：遊戲是回合制，HUD 一秒只變動約兩次，每幀重畫是浪費；HUD 內容幾乎全是文字，Canvas 沒有排版、需要自行測寬、且在 DPR 不符時會糊；Canvas 中的文字對輔助技術完全不存在，而本作是純鍵盤操作。會與 3D 影像合成的效果留在 Canvas，蓋在上層的框與畫面留給 DOM 與 CSS。

需要調整或新增的部分：

- 移動與轉向改為離散補間，不再是連續加速度。
- 步行晃動只在前進補間期間累加，靜止時完全停止。
- 移除 pointer lock 與滑鼠視角。
- **sprite 來源改為載入的 512×512 圖檔，因此新增一個非同步載入階段與 loading 狀態。** 投影、billboard 與 depth buffer 遮蔽的數學不變。
- **sprite 補上與牆面相同的距離衰減與暖色火把加成**；現行實作只有 `globalAlpha` 淡出。
- **命中時依 hurt sprite 產生短暫白色 silhouette VFX**，取代逐片 `ctx.filter`。
- 新增隱藏牆的裂痕 texture 階段。
- 新增溫泉房的暖色光照 override 與蒸氣粒子。
- 新增三色門 texture 與開啟狀態。
- 新增 B4 大房間的高天花板與三門並排構圖；這是全遊戲唯一需要特別取鏡的空間。
- 新增 Block 藍框 VFX 與穿不透的刀彈開動畫。

### 素材歸屬

| 內容                                   | 位置                               | 性質                     |
| -------------------------------------- | ---------------------------------- | ------------------------ |
| 敵人 sprite 母版與離線變體來源         | `assets/enemies/`                  | 可編輯來源，不進 runtime |
| 其他 presentation sprite 原始檔        | `assets/presentation/`             | 可編輯來源，不進 runtime |
| 十五張烘好的 512×512 enemy PNG         | `src/content/enemies/assets/`      | Runtime 素材，經 bundler |
| Player、VFX 與 environment runtime PNG | `src/content/presentation/assets/` | Runtime 素材，經 bundler |

保留原始檔的價值是可以重新烘成其他尺寸；若原始檔是 SVG，還能在版控中 diff。

已知限制不在 V1 處理：牆高一致、無法抬頭低頭、沒有上下層可視、牆上火把不影響環境光、CPU floor casting 在高解析度吃效能。渲染解析度維持 `RENDER_SCALE = 0.55`。若日後要解除這些限制，方向是把 raycasting 改寫成 WebGL fragment shader，而且只會動到 presentation 一層。

戰鬥不含任何隨機數。相同的輸入序列永遠產生相同的結果，這讓 playtest 的每一次死亡都可以精確重現。

## 十七、待驗證問題

以下在第一次可玩版本之後才決定，現在不預先實作：

- 必經路線的壓力、犯錯空間與恢復節奏是否舒服。只以 presentation 的完整人工試玩決定，不設定數值門檻。
- 公主遭遇是否有終局壓迫感但不顯得拖沓。以整體節奏與主觀體感調整，不要求固定傷害比例或成本。
- B4 三岔房間備齊鑰匙就能全開，是否讓那個畫面失去張力。若需要張力，正確的做法是提高上游守鑰匙敵人的價格，不是把門改成二選一。
- 玩家是否看得懂「無法穿透」而不是以為遊戲壞了。若不夠明顯，加上一次性的教學提示。
- 單局是否落在 12–18 分鐘。過短的話擴充 B2 與 B3 的地圖尺寸，不增加系統。
- 溫泉是否太容易被發現。若大部分玩家在 B1 就找到，把它移到 B1 的死路末端而不是主幹道旁。
