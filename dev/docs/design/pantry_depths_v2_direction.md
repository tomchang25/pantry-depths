# Pantry Depths V2 方向

> **狀態**：Draft，未排程。沒有決策就不要動工。
> **性質**：產品方向，不是 forward work。這裡沒有需求、沒有驗收條件、沒有 child。
> **權威邊界**：本文不擁有 V1 的任何契約。[V1 設計文件](pantry-depths_v1.md) 第一節的 Frozen extensions 在 V1 交付前不因本文鬆動一條；本文只記錄「如果之後要做，方向長什麼樣」。

---

## 這份文件在講什麼

V1 是一條線：五層地牢，從 B1 走到 B5，抵達出口就結束。玩家帶不走任何東西，因為根本沒有東西可帶。

V2 的方向是把那條線變成**一趟出勤**——選裝備、下去、拿東西、活著撤出來。同一套確定性戰鬥、同一套格子移動、同一個渲染器，但一局的意義從「通關」變成「這趟賺了還是賠了」。

V1 已經先付掉這個方向最貴的一筆結構債：**結算條件是離開出口，不是擊敗某隻怪。** 那個決定讓「終點」跟「最硬的敵人」變成兩件可以分開擺放的東西，也讓每張地圖用同一種方式收尾——這是撤離玩法的前提，V1 只是剛好也需要它。

## 一、關卡框架

### 起點與出口

V1 已經有：起點是可通行地板上的一個 marker（遊玩時隱藏，編輯器可見），出口是類似樓梯的方塊，按 E 離開並結算。V2 不改這兩者的定義，只是開始利用它們可以被擺在任意位置這件事。

### 出口的解鎖條件

V1 的出口永遠是開的。V2 允許出口需要繳活：

- **擊敗指定敵人**——最直接的一種，把 V1 靠地形擋的事情變成規則擋。
- **啟動開關**——新的 entity kind，一次性、不可逆、不消耗任何資源。

兩者可以組合（打完 A 且按下 B）。開關本身可以被鎖在門後、被敵人擋住，這正是它有趣的地方。

**為什麼這比看起來便宜。** 直覺上「多一個解鎖條件」會讓關卡驗證爆炸，其實不會——爆炸的是鑰匙，不是解鎖。鑰匙**可消耗且可互換**（手上一把紅鑰匙、前面三扇紅門，選哪扇要窮舉），而開關與擊殺 gate 是**單調且不消耗**的：能按就一定按，沒有不按的理由。現行驗證器已經把敵人與可破壞牆歸在這一類——碰到就清掉，不進狀態分支。開關屬於同一類。

### 關卡驗證

不是「檢查開關可達 + 檢查出口可達」兩件獨立的事，而是收斂：

```text
以目前的解鎖狀態跑一次可達
→ 把走得到的開關全按下、走得到的 gate 敵人全清掉
→ 有新解鎖就再跑一次
→ 直到沒有新東西
→ 最後檢查出口是否可達
```

差別在於，如果拿「全部解鎖後的世界」去檢查開關可達，會放過「開關被自己開的那扇門鎖在裡面」這種圖。收斂完就沒事，複雜度是線性的。

### Spawn 條件

Entity 或 block 可以設定 spawn 條件：殺死某隻怪或觸發某個開關之後才出現。

**這是唯一會破壞單調性的機制**，所以要限制。Spawn 出來的東西如果會擋路，它就是不可逆的——殺完怪牆長出來，玩家回不去，關卡直接死鎖，而且驗證器算不出來。

限制方式很乾淨：**只允許 spawn 可清除的東西**，也就是敵人與可破壞牆。這兩者在現行模型裡本來就「碰到就清掉、從不阻擋路線」，spawn 它們不會讓任何格子變不可達，驗證等於不用改。真正的實心牆、鎖住的門不能被 spawn。

剩下的影響只有路線成本（多打幾隻），那是平衡報告的事，不是結構驗證的事。

### 難易度分級

| 等級 | 形狀                                           |
| ---- | ---------------------------------------------- |
| 簡單 | 起點與出口同一側，除非自己做死否則不太可能出事 |
| 普通 | 起點在 1 樓、出口在 5 樓，有可能出事           |
| 困難 | 起點在 1 樓、出口不定，需要額外解鎖條件        |

這是**佈局準則，不是難度選單**。它描述的是一份 floor set 該長什麼樣，不是玩家在主選單上選什麼。V1 只有一份 canonical 五層內容，這張表要成立的前提是「會有很多份地圖」——那本身就是 V2 的框架假設。

## 二、搜打撤

### 出發前整備

下去之前可以整理 Inventory，決定這趟帶什麼。這是一局裡唯一的預先規劃環節，也是「賠了」這件事第一次有意義的地方。

### Item

- 撿到即生效，**不設 Gear 概念**——沒有裝備欄、沒有穿脫、沒有武器切換。
- 放進 Inventory 就開始作用。
- 可以帶出去，跨局保留。

### Blessing

- 該關卡限定的 Buff。
- **撤離即失效**，帶不走。
- 這是「這趟很爽但結束了」與「這趟賺到了」的分界線。

### 詛咒

Item 可以帶詛咒，三種形狀：

- 封鎖所有效果
- 遮蔽所有效果（看不見自己身上發生什麼）
- 增加額外負面效果

詛咒是讓「撿到東西」不再無條件是好事的機制。撿之前要不要賭，就是決策。

### 取得管道

| 門     | 通常放什麼 |
| ------ | ---------- |
| 藍門後 | Item       |
| 黃門後 | Blessing   |

沿用 V1 的顏色語意——藍是攻擊向、黃是防禦向——但把門後的東西從固定數值換成可帶走／不可帶走兩類。紅門維持純開路。

## 三、特殊效果（暫定）

| 效果  | 作用                           |
| ----- | ------------------------------ |
| 踢擊  | 把敵人往後踢一格；撞到尖刺即死 |
| 後退  | 解鎖 `S` 為向後移動            |
| 照明  | 見迷霧；獲得額外視野           |
| CtrlZ | 倒回上一次輸入                 |

三個需要先講清楚的：

**後退直接推翻 V1 的核心定位。** 「在無法後退的地牢裡，用生命買數值」——不能後退產生的那條免費規則（撤退要付兩次轉向的代價）是整個成本模型的一部分。把它做成 item 是可以的，但那等於承認「無法後退」從定位降級成「預設狀態」。這是產品決策，不是功能開關。

**CtrlZ 比想像中便宜。** 確定性契約是「相同輸入序列永遠產生相同結果」，倒回一步 = 重播 N−1 步，兩者完全相容；而 route replay 工具在 `pantry_rules_05` 就已經存在。它需要的是讓 core 擁有 input log，不是讓每個 command 變成可逆的。

**踢擊需要尖刺變成 gameplay entity。** V1 的 `wall-spikes` 是純裝飾（presentation-only environment feature）。踢擊要成立，尖刺得先有規則意義，那是一次契約變更。

## 四、迷霧

地圖可設定迷霧：只看得見三格內的 Floor 與 entity，**2.5D 實景與 2D 地圖同步受限**。

這裡有一個必須先解掉的語意衝突。Feel plan 的 explored map 是「曾經看過就永久保留」，揭露半徑約 2.5 格；迷霧是「當下看得見」。兩者不是同一件事：

| 機制         | 語意       | 記憶     |
| ------------ | ---------- | -------- |
| Explored map | 曾經看過   | 永久保留 |
| 迷霧         | 當下看得見 | 不保留   |

要並存（走過的地方記得，但看不見現在有什麼）還是取代（迷霧外一律不顯示），是產品決策。並存比較符合直覺，也比較難做——它等於要求 2D 地圖同時畫兩層資訊。

照明 item 存在的意義完全建立在這個決定上，所以這題要先於踢擊、後退那些。

## 六、未決問題

1. 迷霧與 explored map 並存還是取代。決定其他所有視野相關內容。
2. 後退是否值得為了一個 item 推翻核心定位。
3. Item 跨局保留代表要有持久化——V1 明文沒有存檔。撤離玩法幾乎必然需要它，這是 V2 最大的一筆架構債。
4. 一趟出勤的長度。V1 是 12–18 分鐘且死亡即整局重來；帶著 Item 下去的一趟如果一樣長，損失感會不會過重。
5. 難易度三級是地圖屬性還是玩家選項。前者是內容分類，後者是 V1 明文不做的難度選擇。
